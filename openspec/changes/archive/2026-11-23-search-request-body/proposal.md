## Why

The storefront currently places the customer's message and conversation ID in the search URL. URL access logs can persist these values. Sending the existing search request as JSON avoids that exposure without adding an analytics or logging pipeline. Basic traffic visibility follows the built-in-only AWS edge specification.

## What Changes

- **BREAKING:** replace `GET /api/v1/search` with `POST /api/v1/search`, using an `application/json` body containing `message`, `conversationId` and optional `clearMemory` (default false).
- Update the backend binding, storefront client, mocks, tests and API documentation together. Do not keep a GET compatibility endpoint.
- Preserve search validation, response bodies/status codes, conversation behavior, rate limits and budgets.
- Ensure the planned CloudFront backend behavior forwards POST requests and their JSON bodies without caching.

## Capabilities

### New Capabilities
- `search-request-transport`: JSON-body transport for the existing search operation across frontend, backend and edge.

### Modified Capabilities
- None in the root canonical specs. Implementation must reconcile the backend/frontend specifications that currently name GET search.

## Impact

Touches `wardrobe-be`, `wardrobe-fe`, API examples and the planned AWS edge configuration. No new services, logging pipeline, analytics changes or search-algorithm changes. This proposal only removes search fields from requests generated by the supported client URLs; it cannot prevent arbitrary callers from putting sensitive values in URLs or prevent explicitly enabled body logging.
